### Trois ADR rédigés et vulgarisés

- `docs/adr/0002-migration-typescript.md` — TypeScript différé. Décision : rester en JavaScript + JSDoc pour le POC. Pourquoi : pas de bénéfice typage proportionné au coût d'apprentissage à ce stade, JSDoc couvre l'autocomplétion sans dépendance supplémentaire.
- `docs/adr/0003-architecture-feature-based-frontend.md` — architecture feature-based progressive (`app/`, `features/`, `shared/`, `services/`). Bloque l'exécution du ticket FE-001B (refactor structurel).
- `docs/adr/0004-react-query-scope.md` — React Query limité aux données serveur métier (catalogue GeoNode, recherche, OGC métadonnées), interdit pour l'instance OpenLayers et son cycle de vie. Bloque l'exécution du ticket FE-007.
- Pourquoi : la SPEC v0.2 fusionnait spécification et décisions structurantes. La séparation en ADR distincts permet à un non-développeur de valider chaque décision indépendamment, et donne aux agents de développement un point d'ancrage stable.

### Dossier `.claude/skills/` créé

- `README.md` (préexistant — désormais cohérent avec le disque).
- `recueil-besoin/SKILL.md` — procédure d'écriture d'un BES (`docs/besoins/BES-AAAA-NNN-<slug>.md`) à partir de notes brutes. Frontmatter prescrit, template 12 sections, règle absolue « décrit le problème, jamais la solution ».
- `spec-fonctionnelle/SKILL.md` — procédure d'écriture d'une SPEC (`docs/specs/SPEC-AAAA-NNN-<slug>.md`) à partir d'un BES validé. Frontmatter `issue_de:` obligatoire, double signature (`valide_par_metier` + `valide_par_tech`), template 22 sections aligné sur SPEC-2026-001. Refus explicite de produire la SPEC si le BES n'est pas en statut `Validé`, sauf cas hybride POC explicitement assumé.
- Pourquoi : sans skills explicites, les futurs livrables BES et SPEC dériveraient en forme et perdraient la traçabilité métier. Les deux skills figent la procédure et le format, et ferment la boucle annoncée par le `README.md` du dossier.

### Conventions méthodologiques actées

- **Frontmatter standardisé** sur tous les livrables Orion : `id`, `version`, `statut`, `valide_par_metier` (+ `valide_par_tech` pour les SPEC), `tags`. Le frontmatter est désormais le point d'ancrage pour les agents (lecture du statut, refus d'enchaînement si non validé).
- **Chemin B (POC hybride)** : un document peut tenir lieu à la fois de BES et de SPEC en phase POC, à condition de porter `type: hybride-poc` et une notice de lecture explicite. Tolérance levée à l'industrialisation.
- **Pas d'enchaînement automatique entre skills** : le passage `Brouillon` → `Validé` exige une action humaine (signature dans le frontmatter). Aucun skill ne déclenche le skill suivant, aucun ticket de SPEC ne s'exécute avant double signature.

### Premier BES réel : édition des couches (extension de session)

- Fichier : `docs/besoins/BES-2026-001-edition-couches-frontend.md` (statut `Brouillon`, dossier `docs/besoins/` créé par la même occasion).
- Origine : demande directe de la direction géomatique en session Cowork (« ajoute dans les fonctionnalités du front la nécessité de pouvoir modifier une couche qui est affichée »).
- Périmètre retenu après questions de cadrage : (1) édition des objets vectoriels — géométrie + attributs ; (2) manipulation du panneau de couches au-delà de l'activation/désactivation (ordre, opacité). Les autres options possibles (style de rendu, métadonnées) n'ont pas été retenues à ce stade.
- BES produit en suivant strictement le skill `recueil-besoin` : 12 sections, 12 questions ouvertes explicitement listées, 6 hypothèses marquées `⟦INFÉRÉ — à valider⟧`. Entretien complémentaire requis avant tout passage en `Validé`.
- Annotation marginale de SPEC-2026-001 (sections 4.2, 4.3, 18) pour pointer le nouveau BES **sans modifier le scope POC** (pas de bump de version, ajout d'une ligne « annotation » à la section 21).
- Pourquoi cette mécanique : la SPEC v0.3 écartait explicitement l'édition du périmètre POC ; intégrer ce besoin dans la SPEC l'aurait étiré et aurait retardé les signatures en cours. Le BES dédié préserve la SPEC en l'état tout en actant que le besoin est désormais formellement instruit.
- Aucun ADR ouvert à ce stade : la décision technique (WFS-T vs API REST custom, politique de conflit, audit) attend la levée des questions ouvertes du BES.
