## 2. Architecture retenue

### Back-end

Plateforme **GeoNode 5** (Django + PostgreSQL/PostGIS + GeoServer + pycsw) installée **comme dépendance pip** (pas comme fork), figée sur un SHA validé. Customisations Orion dans un module Django dédié `src/orion_geonode/`. Stack lancée via `docker compose up -d`. CI GitHub Actions à chaque push, smoke tests sur 4 endpoints sur `master`.

### Front-end

**React 19 + Vite 8 + OpenLayers 10**. JavaScript (pas TypeScript en POC, cf. ADR-0002). Architecture **feature-based** (cf. ADR-0003) :

```txt
front/src/
├── app/        # bootstrap React, providers
├── features/   # map/, layers/, search/, edit/ (futur)
├── shared/     # composants réutilisables, constantes
└── services/   # adaptateurs externes (geonode/, geoserver/, ign-geoportail/, auth/)
```

**Projection principale** : EPSG:2154 (Lambert 93). Web Mercator est secondaire. Fond de carte : **Plan IGN Géoportail WMTS** par défaut, fallback gris en dev, OSM toléré uniquement en dev.

**Gestion du state serveur** : **React Query** (cf. ADR-0004), mais **uniquement** pour les données serveur métier (catalogue GeoNode, recherche, OGC métadonnées). **Interdit** pour l'instance OpenLayers, ses couches en mémoire, ses interactions — elles vivent dans des `useRef` et des hooks impératifs dédiés (`useMapInstance`).

### Méthodologie documentaire

Trois familles de livrables, identifiants annuels :

- **BES** (`docs/besoins/BES-AAAA-NNN-<slug>.md`) — fiche de besoin métier. Décrit le problème, pas la solution.
- **SPEC** (`docs/specs/SPEC-AAAA-NNN-<slug>.md`) — spécification fonctionnelle détaillée. Issue d'un BES validé (sauf cas hybride POC).
- **ADR** (`docs/adr/NNNN-<slug>.md`) — décision d'architecture. Numérotation séquentielle globale.

Flux nominal : `Notes brutes` → skill `recueil-besoin` → BES → **validation humaine** → skill `spec-fonctionnelle` → SPEC → **double signature humaine** → exécution des tickets.

**Aucun skill n'enchaîne sur le suivant.** La transition `Brouillon` → `Validé` exige un acte humain (modification du frontmatter + signature).

## 3. Décisions actées (et leurs arbitrages)

| ID | Décision | Alternatives écartées | Pourquoi |
|---|---|---|---|
| **ADR-0001** | GeoNode comme dépendance pip (pas fork) | Fork complet | Reçoit les mises à jour de sécurité sans effort manuel ; sépare clairement les customisations Orion |
| **ADR-0002** | Rester en JavaScript + JSDoc pour le POC | TS dès maintenant | Coût d'apprentissage non justifié à l'étape POC ; JSDoc suffit pour l'autocomplétion |
| **ADR-0003** | Architecture feature-based progressive | Plat (actuel) ; hexagonal/DDD | Plat ne tient pas la croissance ; hexagonal sur-ingénieré pour un POC |
| **ADR-0004** | React Query limité aux données serveur métier | Pas de React Query ; React Query partout | « Partout » casse le cycle de vie OpenLayers ; « rien » prive du cache utile |
| **Méthodo** | Skills `recueil-besoin` + `spec-fonctionnelle` calibrés sur SPEC-2026-001 | Un seul skill mixte | Sépare le « problème » (BES) du « comment » (SPEC), évite les SPEC orphelines |
| **Méthodo** | Frontmatter standardisé sur tous les livrables (id, version, statut, validation) | Conventions implicites | Point d'ancrage pour les agents qui refusent d'enchaîner si statut non `Validé` |
| **Méthodo** | Chemin B (POC hybride) toléré : un document peut tenir lieu de BES + SPEC en POC | Séparation stricte dès le POC | SPEC-2026-001 est le précédent — on assume, on balise, on séparera à l'industrialisation |
| **Méthodo** | Édition des couches cadrée par BES dédié (BES-2026-001), pas par amendement de SPEC-2026-001 | Greffer dans SPEC v0.3 | Aurait étiré le scope POC et relancé les signatures |

### Cycle de vie des statuts (à formaliser dans les skills)

- **BES** : `Brouillon` → `Validé` → `Obsolète` ou `Remplacé par BES-XXX`. Une signature (`valide_par_metier`).
- **SPEC** : `Brouillon` → `Brouillon avancé` → `Validé` → `En révision` (re-ouverture) → `Validé` à nouveau ; ou `Obsolète` / `Remplacé par SPEC-XXX`. Deux signatures (`valide_par_metier` + `valide_par_tech`).
- **ADR** : `Proposé` → `Accepté` → `Déprécié` / `Remplacé par ADR XXXX`. Pas de signature, validation par l'`architecte-orion`.

## 4. Conventions du projet

- **Langue** : français.
- **Vulgarisation prioritaire** : l'utilisateur principal est directeur d'équipe géomatique, pas développeur. Tout terme technique est défini à sa première apparition.
- **Pourquoi avant comment** : motiver une décision avant de décrire la procédure.
- **Branches** : jamais de commit direct sur `master`. Toujours branche + PR.
- **Secrets** : variables d'environnement uniquement. `.env.sample` avec placeholders seulement.
- **Code** : Python 3.11+ (PEP 8 / black / flake8), React fonctionnel (hooks, pas de classes), Vitest côté front, pytest côté back.
- **Pas de retour à Esri** : l'objectif est explicitement l'open source. Pas de proposition propriétaire.
- **Identifiants** : BES et SPEC numérotés annuellement (`BES-2026-NNN`, `SPEC-2026-NNN`) ; ADR numérotés globalement (`NNNN-<slug>.md`). Slugs en kebab-case, sans accent.
